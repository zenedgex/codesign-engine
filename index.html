The problem

Stop choosing chip architectures by guesswork.

The decisions that shape an accelerator, its array, memories, dataflow, precision and how the compiler maps the model onto it, are made early, when the least evidence is available. Teams can afford to evaluate only a handful of candidates, and changing course after implementation starts costs months.

Atelier Studio lets you explore far more hardware configurations against your actual AI workloads, performance targets, area limits and power budget, before committing to expensive implementation cycles.

  • Explore more design alternatives
  • Find better workload-to-hardware mappings
  • Reduce manual design-space exploration
  • Evaluate trade-offs with measurable evidence

The solution

One search across workload, hardware and compiler.

A chip is only as good as the program that runs on it. Atelier Studio gives every candidate architecture its own compiler search, so designs are compared on how your workload will actually execute, not on peak numbers.

  1. Workload and constraintsYour model and its frame or token rate, power, area and latency targets
  2. Candidate architecturesEngines, array, memories and dataflow, from a reference architecture or your own RTL blocks
  3. Compiler mappingFor each candidate, the compiler builds that design's mapping space, searches it and compiles its best program
  4. Evaluation in tiersFast estimate, then the SoC model; RTL simulation, synthesis and floorplan for the designs worth it
  5. Ranked designsThe designs that meet your targets, ranked by what you care about most, each with its evidence

RTL-verified

Results or cycle counts checked against a reference, in cycle-accurate simulation of the generated RTL. The tested scope is stated with each result.

Integer model

Measured in software with the accelerator's exact integer arithmetic, which the RTL matches bit for bit on the frames checked.

Model-estimated

Performance, power or area from Atelier Studio's models; their assumptions and calibration are stated with each table.

Floorplan-evaluated

Synthesis and floorplan with OpenROAD-flow-scripts on the ASAP7 predictive kit. Not fabricated silicon, not a foundry process.

Evidence · language models

Qwen3-0.6B, a whole token on the RTL.

Every matrix multiply of a generated token on the generated RTL, with Qwen3-0.6B's real shapes; the norms, softmax and RoPE in our integer spec beside it. Then Sutra sized from one engine to eight for the token rate you need.

645 / 645matrix multiplies of a whole token, all 28 layers and the output head, run on the RTL bit-identical; the logits equal the integer reference, the other ops computed in its integer arithmetic (16.8 million cycles, cycle model within 0.004%)
13 / 13distinct matrix shapes of a token and of a 512-token prompt, run on the RTL with random INT8 data, bit-identical to the integer reference
0.2%cycle estimate against the RTL over a whole token and a whole prompt (18.4 and 84.1 million cycles; every shape within 1%)
20.5 msengine time per generated token at 900 MHz: 49 tokens/s when memory keeps up

Model: Qwen3-0.6B (28 layers, grouped-query attention), INT8 weights and activations; wider layers split into 1,024-channel parts; attention run as matrix multiplies with K and V loaded at run time. Hardware: one 64×64 engine, simulated in Verilator, its weights and commands fed one per cycle by the test bench: the job of a planned weight DMA and command queue (the RISC-V control core alone takes about ten cycles per command). Not yet on chip: RMSNorm, softmax, RoPE and the SwiGLU multiply, which the estimates below cost on proposed units. Weights here are random: function and timing, not answers. With the real weights, a simulation of Sutra's number formats shows a correct reply needs a 16-bit residual stream and per-token activation scales (planned).
